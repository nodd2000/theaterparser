# Theaterparser — план проекта

Агрегатор информации о новых постановках по России (по образцу nachtkritik.de):
база спектаклей + сводка прессы по каждой премьере. Первичный источник — Telegram-каналы
(театры, критики, блогеры, журналисты), позже — сайты театров.

---

## 1. Что берём у nachtkritik.de

| nachtkritik | У нас |
|---|---|
| Каждая значимая премьера получает карточку | Карточка спектакля: театр, сцена, дата премьеры, автор/первоисточник, постановщики, состав, жанр, возраст, фото |
| Nachtkritik — рецензия в ночь премьеры | Первые отклики из TG-каналов критиков, привязанные к спектаклю |
| Presseschau — обзор чужой прессы | «Пресса о спектакле»: цитаты из рецензий + ссылки на источник, автор, издание/канал |
| Календарь премьер, навигация по городам/театрам | Фильтры страна → город → театр, календарь премьер, лента «новое за неделю» |
| Страницы режиссёров и театров | Страницы театров, персон (режиссёры, художники, актёры), критиков/источников |

Систематичность = единая схема данных для каждой постановки и обязательная привязка
каждого упоминания (пост, рецензия, фото) к конкретному спектаклю.

## 2. Архитектура

```
 Telegram (MTProto)          Сайты театров (фаза 2)
        │                            │
        ▼                            ▼
 ┌──────────────┐            ┌──────────────┐
 │ tg-collector │            │ web-collector│      демоны сбора
 └──────┬───────┘            └──────┬───────┘
        └────────────┬──────────────┘
                     ▼
            raw_posts (PostgreSQL, неизменяемые) + медиа (S3/MinIO)
                     │  очередь задач (Redis + arq/Dramatiq)
                     ▼
 ┌─────────────────────────────────────────────┐
 │ processor                                    │
 │  1. классификация: премьера/анонс/рецензия/  │
 │     фото/новость/нерелевантно                │
 │  2. извлечение сущностей (LLM, JSON-схема)   │
 │  3. сопоставление с базой (театр, спектакль, │
 │     персоны): pg_trgm + правила + LLM        │
 │  4. уверенность ≥ порога → публикация,       │
 │     иначе → очередь модерации                │
 └──────────────────┬──────────────────────────┘
                    ▼
            PostgreSQL (каталог)
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   FastAPI (публичный API)   Админка/модерация
          │
          ▼
        Сайт
```

### Стек
- **Python 3.12**, `uv` для зависимостей, монорепо.
- **FastAPI** + Pydantic v2 — API.
- **PostgreSQL 16**: SQLAlchemy 2 (async) + Alembic; `pg_trgm` для нечёткого поиска названий,
  полнотекстовый поиск с русской морфологией.
- **Redis** + **arq** (или Dramatiq) — очередь обработки.
- **Telethon** — чтение каналов через пользовательский аккаунт (Bot API не умеет читать чужие каналы).
  Резерв для публичных каналов без аккаунта — веб-превью `t.me/s/<channel>`.
- **LLM** для классификации/извлечения (structured output). Дешёвая модель на классификацию,
  более сильная — на извлечение из релевантных постов. Альтернатива без внешних API —
  Natasha/правила, но качество заметно ниже.
- **MinIO/S3** — фото.
- **Фронтенд**: см. вопрос 9. По умолчанию — серверный рендеринг (SEO критичен для такого каталога).
- **Docker Compose** для локального запуска и деплоя.

### Сервисы (процессы)
1. `collector-telegram` — подписка на новые сообщения + периодический догоняющий проход по
   `last_message_id` каждого канала; первичная выгрузка истории (backfill) с ограничением
   скорости, обработка FloodWait; сохраняет пост «как есть» (текст, entities, медиа, репосты,
   правки, альбомы как одна группа).
2. `processor` — воркеры очереди (шаги 1–4 выше). Идемпотентны, можно перепрогонять при
   изменении промптов/правил.
3. `api` — публичный REST API + API админки.
4. `web` — сайт.
5. `scheduler` — периодические задачи (догонялка, пересчёт статусов «премьера → в репертуаре»,
   обновление справочников).

## 3. Модель данных (черновик)

- **Country**, **City** (регион, координаты).
- **Theatre**: название, альтернативные названия, тип (гос./частный/независимый), жанр
  (драма, опера/балет, кукольный, ...), город, сайт, официальные TG-каналы.
  **Stage** — сцены/площадки театра.
- **Person**: ФИО, варианты написания, роли (режиссёр, художник, хореограф, актёр, критик…).
- **Production** (спектакль): название, театр, сцена, первоисточник/автор, жанр, возраст,
  дата премьеры (+ даты предпремьерных показов), статус (анонсирован / премьера / в репертуаре /
  снят), описание, ссылки на билеты.
  **ProductionCredit**: персона + роль в постановке.
- **Source**: TG-канал или сайт; тип (официальный театра / критик / блогер / СМИ / фестиваль),
  связь с Theatre или Person, вес/доверие, активен ли сбор.
- **RawPost**: источник, внешний id, дата, текст, медиа, ссылки, хэш, версия правки.
- **Mention**: RawPost ↔ Production, тип (анонс, премьера, рецензия, фото, интервью, новость),
  уверенность, статус модерации.
- **Review**: автор (Person), источник, ссылка, дата, цитата/выжимка, (опционально) тональность.
- **Media**: фото, автор фото (кредит), связь с Production и RawPost.
- **Festival / Award** (Золотая маска и т.п.) — опционально, фаза 3.

Принцип: сырые данные не меняются; всё извлечённое — производное, с указанием
источника и версии экстрактора, чтобы можно было переобработать.

## 4. Ключевые сложности

1. **Сопоставление сущностей.** Один спектакль называют по-разному («Гамлет» в МХТ,
   «Гамлет. Коллаж», «новый Гамлет Богомолова»). Нужны: справочник театров с алиасами,
   нечёткий поиск, учёт контекста (канал театра → его спектакль), ручное слияние в админке.
2. **Справочник театров.** Без стартового справочника привязка будет плохой. Варианты
   наполнения: Культура.РФ / открытые данные Минкультуры, Wikidata, ручной список.
3. **Шум.** Большая часть постов театральных каналов — не про новые постановки
   (розыгрыши, дни рождения, гастроли). Классификатор отсекает до извлечения — это и экономия.
4. **Telegram-аккаунт.** Риск блокировки при агрессивном чтении. Отдельный аккаунт,
   лимиты, постепенный backfill.
5. **Авторское право.** Полные тексты рецензий и фото без разрешения публиковать нельзя.
   По умолчанию — цитата + ссылка на пост, фото — встраивание поста или с разрешения.
6. **Доступность сервисов из РФ/за РФ.** Внешние LLM API, Telegram, хостинг — выбор
   юрисдикции хостинга влияет на всё (см. вопросы).

## 5. Этапы

**Фаза 0 — каркас (1 неделя)**
Репозиторий, Docker Compose (Postgres, Redis, MinIO), схема БД + миграции, CI (ruff, mypy, pytest).

**Фаза 1 — сбор (1–2 недели)**
Telethon-коллектор, реестр каналов (CSV/админка), backfill + live, хранение raw-постов и медиа.
Результат: все посты выбранных каналов в базе.

**Фаза 2 — обработка (2–3 недели)**
Классификатор, экстрактор, сопоставление с театрами/спектаклями, очередь модерации,
минимальная админка (подтвердить / исправить / слить дубли). Набор размеченных постов
для оценки качества (precision/recall по типам).

**Фаза 3 — сайт MVP (2–3 недели)**
Каталог: страна → город → театр → спектакль; карточка спектакля с «Прессой»;
календарь премьер; лента новых; поиск; страницы театров, персон, источников; RSS.

**Фаза 4 — развитие**
Сайты театров (афиши, официальные данные о составе), фестивали/премии, подписки и
уведомления (в т.ч. TG-бот с дайджестом), собственная редакция/рецензии, учётные записи.

## 6. Уточняющие вопросы

### Охват
1. Только **новые постановки** (премьеры с какой-то даты) или весь текущий репертуар?
   С какой даты делать backfill истории?
2. «Выбирать страну» — какие страны кроме России? СНГ, русскоязычные театры за рубежом?
3. Какие виды театра входят: драма, опера/балет, кукольный, мюзикл, независимые
   проекты/сайт-специфик, иммерсивные, фестивальные постановки, антрепризы?
4. Нужны ли страницы персон (режиссёры, актёры) с фильмографией-«театрографией», фестивали
   и премии?

### Источники
5. Есть ли готовый список каналов? Примерный масштаб: десятки, сотни, тысячи?
6. Есть ли готовый справочник театров, или собираем сами (Культура.РФ / Wikidata / вручную)?
7. Готовы выделить отдельный Telegram-аккаунт (номер телефона) под парсер?
   Нужны ли закрытые каналы или только публичные?
8. Насколько важна оперативность: появление на сайте через минуты или раз в несколько часов достаточно?

### Контент и право
9. Публикуем полные тексты рецензий или цитату + ссылку? Фото — перезаливаем к себе
   (нужны разрешения) или встраиваем посты/ссылки?
10. Будет ли собственная редакция (свои рецензии, как у nachtkritik), или чистая агрегация?
    Комментарии пользователей?
11. Публикация автоматически при высокой уверенности или каждое извлечение проходит через
    модератора? Кто будет модерировать и сколько времени на это есть?

### Технические
12. Можно ли использовать платный внешний LLM API (качество извлечения сильно выше) и
    какой месячный бюджет допустим? Или только локальные/бесплатные решения?
13. Где хостинг: Россия или за рубежом? От этого зависит доступность LLM API, Telegram,
    требования 152-ФЗ, домен.
14. Фронтенд: серверный рендеринг на Python (Jinja2 + HTMX, один язык во всём проекте)
    или отдельное SPA/SSR-приложение (Next.js)? Есть ли дизайнер/макеты?
15. Нужны ли учётные записи пользователей (избранное, подписки на театры/города,
    уведомления)? Нужен ли открытый API для третьих лиц?
16. Язык интерфейса — только русский или ещё английский?
17. Есть ли ограничения по инфраструктуре (бюджет на сервер, предпочтения по облаку)?
